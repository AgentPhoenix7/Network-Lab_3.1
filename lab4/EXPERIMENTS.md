# Assignment 4 — Experiment Designs

The assignment PDF names no metrics, so every experiment below was
chosen by us.

**Selected for the report: E1 and E3.** E2 and E4 are designed but
**not built**. The report mentions them under "possible improvements".
To promote one, the user has to say so explicitly. Then add a milestone
to `PLAN.md` and tests to `tests/tests.md`.

Common setup for every experiment:
- Processes run over loopback TCP.
- Input files are random bytes generated by `run_eval.py` from a
  master seed (default 42) into `eval/data/`, which is gitignored.
- Each run gets a distinct port (9400 + run index mod 500).
- Python only launches binaries and parses metrics files and CSVs
  (CLAUDE.md R1).

## E1 — Correctness sweep  ✅ SELECTED

**Question:** does every receiver reconstruct its sender's data
exactly, for any n, including n that isn't a power of 2, unequal file
sizes, and senders that are silent part of the time?

| parameter | values |
|---|---|
| n | 1, 2, 3, 4, 5, 7, 8, 9, 15, 16, 17, 31, 32 |
| L | `walsh_length_for(n)` (from the channel metrics, never computed in Python) |
| file size for sender i | `1000 + 997·i + rand(0..43)` bytes: unequal, and not multiples of 44 |
| late start | sender `n−1` gets `--start-round 3` when n ≥ 2 |
| trials | 3 (seed = master + 1000·n + trial) |

**Per-run checks (all must hold):**
- `cmp in_i out_i` succeeds for every i;
- receiver `fcs_fail = seq_errors = error_frames = bits_invalid = 0`;
- `frames_ok_i = ceil(size_i / 44)`;
- `silent_rounds_i = rounds − frames_ok_i`;
- channel `max_abs_sum ≤ n`;
- every process exits 0.

**CSV** `eval/EVAL_E1.csv` has one row per (run, station):
```
n,L,trial,seed,station,file_bytes,rounds,frames_ok,fcs_fail,seq_errors,
error_frames,silent_rounds,bits_one,bits_zero,bits_silent,bits_invalid,
max_abs_sum,match
```

**Report outputs:**
- **Table E1**: per n, list L, total frames, total bytes, match %, and
  the invalid-bit total. We expect 100% match and 0 invalid bits.
- **fig_e1_decisions.png**: a stacked bar of the per-bit decision
  classes (ONE / ZERO / SILENT / INVALID) summed per n. INVALID
  should be visibly zero.
- **fig_walsh.png**: two panels, a heatmap of `W_8` and a heatmap of
  `W_8·W_8ᵀ` (which is `8·I`). The data comes from `tools/walsh_dump 8`.

## E3 — Efficiency / throughput  ✅ SELECTED

**Question:** what does code-division sharing cost? How does each
station's rate, and the total useful rate, scale with n?

### E3a — Analytic (no processes)
For n = 1..64:
- per-station rate fraction = `1/L(n)` of the chip rate
  (the bandwidth expansion is L);
- code utilisation = `n/L(n)`. It is 1 at powers of 2 and drops to
  about 0.5 just after each one.
- Frame efficiency is the constant `44/65 = 0.677`, so useful rate =
  `(44/65)·(1/L)` per station.

`L(n)` comes from `tools/walsh_dump --lengths 64` (prints `n,L`), so
Python doesn't re-implement `walsh_length_for`.

**fig_e3_analytic.png**: step plot of `1/L` and `n/L` vs n, with
vertical markers at 2^k + 1.

### E3b — Measured (processes)
| parameter | values |
|---|---|
| n | 1, 2, 3, 4, 6, 8, 12, 16, 24, 32, 48, 64 |
| file size | 16 KiB per sender (373 frames), all equal, no late start |
| trials | 3 |

From the metrics files:
- `elapsed_s = channel.elapsed_ns / 1e9`
- `goodput_station_bps = file_bytes·8 / elapsed_s`
- `goodput_total_bps = n · goodput_station_bps`
- `chip_rate_cps = rounds · 520 · L / elapsed_s`, the chips
  per second one sender's link carries
- `round_us = elapsed_ns / rounds / 1000`
- `sum_share = sum_ns / elapsed_ns`, the fraction of time spent
  computing versus doing I/O

**CSV** `eval/EVAL_E3.csv`, one row per run:
```
n,L,trial,seed,file_bytes,rounds,elapsed_s,sum_s,round_us,
goodput_station_bps,goodput_total_bps,chip_rate_cps,code_util
```

**Figures:**
- **fig_e3_goodput.png**: per-station and total goodput vs n (mean ±
  min/max over trials), with the shape predicted by `1/(n·L)`
  overlaid and normalised at n=1.
- **fig_e3_round_cost.png**: `round_us` vs `n·L`, with a linear fit.
  Each round the channel reads n·520·L bytes and writes n·1040·L
  bytes, so the cost should be linear.

**Caveat for the Analysis section.** Measured goodput is simulation
throughput on loopback. It is dominated by socket I/O, not by radio
physics. The shape vs n is the result. Absolute bits/s are not.

## E2 — Noise robustness  ⏸ DEFERRED (not built)

**Question:** how does the spreading gain protect data when the medium
is noisy?

- Add AWGN to `S[k]` inside the channel, which needs a `float` sum
  path, or flip chips of `S` with probability q. Receivers decide by
  **sign** of corr instead of exact equality, and count bit errors
  against a known pattern.
- Sweep SNR (Eb/N0) from −4 to 10 dB for L ∈ {4, 16, 64}, with fully
  loaded n = L.
- Figure: BER vs Eb/N0 per L. The expected effect is more processing
  gain as L grows at a fixed chip SNR.
- **What it would take:** a `--noise` option in `channel`, a
  `cdma_decide_soft()` in `cdma.c`, and a BER counter in `receiver`.
  It breaks the exact `{±L, 0}` invariant, so the E1 checks must turn
  it off.

## E4 — Orthogonality breakdown  ⏸ DEFERRED (not built)

**Question:** why do real CDMA systems need synchronisation and power
control?

- **Asynchrony:** shift sender j's chips by d ∈ {0..L−1} chips relative
  to the others before summing. Walsh codes are poor at non-zero
  lags, so `bits_invalid` and BER jump as soon as d ≠ 0.
- **Near-far:** scale sender j's amplitude by A ∈ {1, 2, 4, 8}. It is
  still exact when synchronous, which shows that orthogonality survives
  unequal power. Combined with asynchrony, the strong station swamps
  the weak one.
- Figures: `bits_invalid` rate vs chip offset d, and BER vs A with
  d > 0.
- **What it would take:** per-sender `--chip-offset` and `--gain`
  options applied in the channel before `cdma_sum`. That changes the
  `cdma_sum` contract, so it needs an explicit decision.
